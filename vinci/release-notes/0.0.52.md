Two fixes, both about a message you sent going somewhere you couldn't see.

**A credential you type now actually works.** Vinci redacts secrets before they reach the model, so a real key is never painted across your screen or written into a session file. But it was doing that to credentials *you* deliberately handed it — paste a working `curl` with a bearer token and ask Vinci to run it, and the model received `Authorization: Bearer <vinci-secret>`, then sent that literal text to the real endpoint and got a 401. The same thing put `<vinci-secret>` into real environment variables. It read like a broken API rather than like a masked view.

A secret you type is now held for the session and given a name — `<vinci-secret-a1b2c3d4>` — and the shell puts the real value back at the moment the command runs. The model still never sees it. Three limits, deliberately: the substitution happens for shell commands only, so a credential is never written into a file on the model's initiative; only what *you* typed is held this way, so a secret Vinci found by reading your `.env` stays a dead end it cannot reverse; and Vinci tells you which credentials it restored into a command, naming the handles and never the values. The store is cleared when the session ends and never touches disk.

Commands that carry a placeholder Vinci *can't* resolve — one standing for a value it only read, or a name the model invented — are refused before they run, instead of failing against a live endpoint.

**Queued messages stop claiming to be queued after they've been sent.** Typing while Vinci was working showed "Queued for Vinci · 4 messages" above the composer, and the count kept climbing even though every one of those messages had already been delivered and answered. The widget was matching messages by their text, which changes on the way to the model — a redacted secret, an attached image path, an expanded `/command` — so a delivered message was never recognised as the one that had been waiting. It also had no way to notice that pressing Esc, or pulling the queue back into the composer, had emptied the queue without sending anything.

The count now comes from the session itself, so it is right in all of those cases.
